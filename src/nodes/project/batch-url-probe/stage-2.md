# 第二阶段：异步探测

## 实现要求

- 保留 `url-probe-sync` 的源码和行为，在 `Cargo.toml` 中新增名为 `url-probe-async` 的 bin。
- 使用 Tokio 运行时和 reqwest 异步接口实现新版本；不得用异步任务包裹阻塞 reqwest 接口冒充异步请求。
- 使用与同步版相同的 URL 列表、GET 方法、成功判定、超时值和输出字段，仍不读取响应正文。
- 让多个请求在等待网络响应时重叠执行，并设置明确的并发上限。上限写在代码常量中，URL 数量必须大于该上限。
- 单项计时从取得并发名额、实际开始请求时计算，不包含排队等待名额的时间；总耗时覆盖整个批次。
- 每个目标完成后即可输出，顺序不必与 URL 列表一致。
- 一个请求失败或超时不得取消其他请求；全部任务结束后输出成功数、失败数和总耗时。
- 为不依赖网络的成功判定和汇总逻辑保留或补充单元测试。

不要求实现并发度、URL 或超时的命令行配置，也不要求用固定倍数证明异步版更快。

## 交付要求

在第一阶段交付物基础上：

- `Cargo.toml` 同时登记两个 bin，并包含异步版需要的依赖和 feature；
- README 说明两个 bin 的运行方式、并发上限和异步输出顺序；
- README 记录在相同目标、超时和环境下运行两版的结果与总耗时，并简要解释差异；
- 同步版仍可独立构建和运行。

提交前应确认代码已经格式化、Clippy 无警告、测试通过且两个 bin 均能构建。随后运行：

```sh
cargo build --bins
cargo run --bin url-probe-sync
cargo run --bin url-probe-async
```

两个版本均通过验收后，在最终提交上创建并推送 `stage-2-async` tag。最终 GitHub 仓库必须同时包含可用的 `stage-1-sync` 和 `stage-2-async`。
