# 第二阶段流程提示

## 1. 固定同步基线

开始修改前，确认 `stage-1-sync` 指向完整、可构建的同步版本，README 中保留了测试条件和一次运行结果。第二阶段不能以删除同步实现换取更简单的项目结构。

## 2. 建立异步模型

先理解以下概念，再修改请求循环：

- `async fn` 返回的 future 在何时取得进展；
- `.await` 表示可能暂停当前任务，不等于创建线程；
- Tokio 运行时和 task 各自负责什么；
- 并发与并行的区别；
- 为什么网络等待适合异步，以及为什么并发仍需上限；
- 任务完成顺序为什么可能不同于创建顺序。

优先阅读 Rust Book 的[异步编程章节](https://doc.rust-lang.org/book/ch17-00-async-await.html)和 Tokio 教程的[任务与并发](https://tokio.rs/tokio/tutorial/spawning)。遇到所有权或 `Send` 相关错误时，先判断哪个值需要跨越 `.await`，不要直接增加无关的复制或共享状态。

## 3. 增加第二个 bin

阅读 Cargo Book 的 [Cargo Targets](https://doc.rust-lang.org/cargo/reference/cargo-targets.html)，理解一个 package、bin target、bin crate 和源码路径之间的关系。然后：

- 在 Cargo 配置中保留同步 bin，并登记异步 bin；
- 添加 Tokio 和异步 reqwest 所需的依赖与 feature；
- 先让新 bin 能独立构建，再迁移请求逻辑；
- 不急于抽取共享库。少量重复有助于直接比较两个版本。

## 4. 从一个异步请求扩展到有界并发

先完成一个异步 GET 请求，确认状态、错误和计时语义与同步版一致。随后再处理整组 URL：

1. 明确并发名额在何处取得和释放。
2. 取得名额后再开始单项计时。
3. 启动多个异步请求并收集每个结果。
4. 目标一完成就释放名额，使排队目标可以开始。
5. 等待全部任务结束后再输出汇总和总耗时。

并发上限可以用适合的 Tokio 原语或有界流实现。阅读所选 API 的官方文档，例如 [`Semaphore`](https://docs.rs/tokio/latest/tokio/sync/struct.Semaphore.html)，但不要同时引入多套并发方案。

重点检查异步版确实使用 reqwest 的异步 client；把阻塞请求放入 async 函数不会自动变成异步 I/O。

## 5. 比较两个版本

在相同机器和网络环境中，使用[项目总览](./index)给出的正式验收集分别运行两个 bin，并满足：

- 两版对各目标的分类和汇总计数一致；
- 异步版的完成顺序允许变化；
- URL 数量大于并发上限，可以观察分批执行；
- 多个延迟请求发生重叠，异步版总耗时明显小于同步版；
- 不以一次公共网络测量或固定加速倍数作为结论。

若结果不符，先检查测试目标是否稳定、计时边界是否一致、请求是否真正并发，再检查输出和汇总逻辑。

## 6. 收尾和验收

更新 README，保留两版的运行条件、结果、耗时和简短解释。再次检查同步 bin 没有被第二阶段改坏，所有质量检查通过后再创建 `stage-2-async` tag。

使用 AI 时，适合询问 future 为什么未执行、所有权为何跨越 `.await`、并发上限是否真正生效。最终判断仍以官方 API 文档、编译器、测试和可观察结果为准。
