# `.gitignore` 文件的使用

`.gitignore` 用于声明不需要纳入 Git 版本管理的文件。被忽略的未跟踪文件不会出现在普通的 `git status` 结果中，也不会被 `git add .` 加入暂存区。

## 机制与语法

在仓库根目录创建 `.gitignore`，可以写入如下规则：

```gitignore
# 井号开头的行是注释。

# 忽略所有名为 `.DS_Store` 的文件，包括子目录中的：
.DS_Store

# 忽略 `build` 目录：
build/

# 忽略 `.vscode` 目录下的所有文件，但不包括 `.vscode` 目录本身：
.vscode/*
# 使用 `!` 取反，表示不忽略：
!.vscode/extensions.json

# 忽略所有扩展名为 `.exe` 的文件：
*.exe

# `*` 匹配任意非 `/` 字符，`**` 匹配任意目录层级。
# 忽略 `docs` 目录下所有 PDF 文件，包括子目录中的：
docs/**/*.pdf

# 忽略所有扩展名为 `.pyc`、`.pyo`、`.pyd` 的文件：
*.py[cod]
```

修改规则后运行 `git status`，应当不再看到符合规则的未跟踪文件。`.gitignore` 只影响尚未被 Git 跟踪的文件；已经进入版本记录的文件不会因为新增忽略规则而停止被跟踪。

### 多个 `.gitignore`

一个 Git 仓库中可以有多个 `.gitignore`。

根目录的 `.gitignore` 可以管理整个仓库，子目录中的 `.gitignore` 则从该子目录开始作用于其后代。通常先把通用规则放在根目录，只有子目录需要独立规则时才增加新的 `.gitignore`。

## 如何判断文件是否需要忽略

依次考虑以下问题。

#### > 是否需要纳入版本管理

源代码、必要配置、文档等构成项目的文件通常需要纳入版本管理。编译产物、缓存和可以重新下载的依赖通常不需要，它们会增加无意义的版本变化或仓库体积。

有些文件可提交也可忽略。此时应比较它带来的协作价值和维护成本：如果提交后能固定项目状态、提高可复现性，通常应当提交；如果内容可以稳定生成，而且频繁变化却不能帮助理解项目，通常应当忽略。

#### > 是否适合共享

团队成员都需要的配置应当提交，例如统一的格式化规则。只描述个人电脑的文件路径、编辑器界面偏好或本机临时状态的配置通常应当忽略。

不要仅根据文件是不是“配置文件”作判断。同一个工具的配置中，团队规则可能需要共享，个人路径则不适合共享；必要时应拆分为公共配置和本地配置。

#### > 是否可以上传到远程仓库

密码、访问令牌、私钥和含个人信息的数据不得上传到 GitHub 等远程仓库。可以提交一个不含真实值的示例文件，说明项目需要哪些配置项。

### 示例

| 文件或目录                   | 通常如何处理 | 原因                                     |
| ---------------------------- | ------------ | ---------------------------------------- |
| `src/motor_control.c`        | 提交         | 源代码是项目本身，需要版本记录和协作     |
| `firmware/build/control.elf` | 忽略         | 编译产物可以从源代码重新生成             |
| `.env`                       | 忽略         | 环境变量文件，可能包含真实密码或访问令牌 |
| `.env.example`               | 提交         | 用占位值说明所需配置，不包含真实秘密     |

## 【检查题】

1. 了解 `.DS_Store` 文件的作用。为什么通常需要忽略它？
2. `.gitignore` 文件本身会被 Git 跟踪吗？
3. 如果你之间前已经把 `temp.cpp` 提交到了仓库，但现在想忽略它，应该怎么做？
4. 有些仓库会选择包含 `.vscode/settings.json`，有些则会选择忽略它。有哪些原因支持忽略它，又有哪些原因支持提交它？有什么方法可以缓解这一矛盾？
5. `.env` 文件通常包含敏感信息。如果你之前已经把它提交到了仓库，但现在想忽略它，应该怎么做？你的做法安全吗？
6. `.env` 文件有时候会包含一些你和团队成员都需要的敏感配置项，例如数据库连接字符串。有什么办法，既能满足团队协作，又能保护敏感信息？调研一下。
