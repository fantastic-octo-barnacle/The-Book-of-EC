# 观察、暂存与提交

Git 的日常本地操作只有一个固定顺序：观察修改、选择内容、再次检查，然后提交。不要在不清楚状态时连续执行修改仓库的命令。

## 先查看状态

```sh
git status
```

`git status` 会列出当前分支，以及已修改、已暂存和未跟踪的文件。它不展示文件具体改了什么。

查看已跟踪文件在工作区中的具体修改：

```sh
git diff
```

新创建但尚未暂存的文件属于“未跟踪文件”，`git status` 会列出它，`git diff` 默认不会展示它的内容。

## 选择下一次提交的内容

按明确路径暂存准备提交的文件：

```sh
git add src/main.c
```

检查暂存区中将要提交的修改：

```sh
git diff --staged
```

`git diff` 与 `git diff --staged` 回答不同问题：

| 命令                | 比较的内容       |
| ------------------- | ---------------- |
| `git diff`          | 工作区与暂存区   |
| `git diff --staged` | 暂存区与当前提交（`HEAD`） |

如果暂存后又编辑了同一个文件，先前暂存的版本不会自动更新。再次执行 `git add <path>` 才会用当前工作区版本替换暂存区版本。

::: tip 为什么示例不直接使用 `git add .`
`git add .` 会暂存当前目录下的全部变化，容易把调试输出、临时文件或不相关修改一起带入提交。先用 `git status` 检查，再按路径选择，意图更明确。
:::

## 创建提交

确认 `git diff --staged` 只包含本次需要保存的修改后，创建提交：

```sh
git commit -m "修正编码器方向判断"
```

提交只保存暂存区中的内容。仍留在工作区的修改不会消失，也不会进入这次提交。

提交信息应简短说明这次提交完成了什么。不要使用“update”“修改一下”这类无法区分提交目的的描述。

## 查看历史

```sh
git log --oneline -n 5
```

每行开头的字符是提交 ID 的缩写，后面是提交信息。最新提交通常位于最上方。再次执行 `git status`，应能确认是否仍有未提交修改。

## 【检查题】

1. 为什么执行 `git add` 后还需要查看 `git diff --staged`？
2. 同一文件为什么可能同时出现在“已暂存”和“未暂存”两组中？
3. 提交完成后，工作区里未暂存的修改会发生什么？
